## 本机环境（实测）

| 项 | 实际值 | 备注 |
|---|---|---|
| cargo / rustc | `C:/Users/kkw/.cargo/bin/cargo.exe` | **不在 PATH 里**，需绝对路径调用 |
| rustc 版本 | 1.99.1，host `x86_64-pc-windows-gnu` | host 是 GNU，但构建必须用 MSVC target |
| 目标三元组 | `x86_64-pc-windows-msvc` | `.cargo/config.toml` 与 `rust-toolchain.toml` 双处固定 |
| MSVC | `C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools`，VC 14.44.35207 | 是 **x86 的 Program Files** |
| Windows SDK | 10.0.26100.0 | 提供 `rc.exe` |
| 构建产物目录 | `C:/Users/kkw/cargo-target/deskagent` | `.cargo/config.toml` 中 `target-dir` |

两条容易误判的地方：

1. **"没装 MSVC" 是查错目录得出的错误结论。** 64 位 `C:\Program Files` 下没有，
   但 32 位的 `Program Files (x86)` 下有完整 Build Tools。判断前先查两个位置。
2. **`cargo check` 通过不代表能构建。** GNU host 下链接阶段才会因缺少 `dlltool` 失败，
   必须显式固定 MSVC target。

`rust-toolchain.toml` 里**故意不声明** `components = ["rustfmt", "clippy"]`：rustup 每次进入
项目目录都会校验并尝试补装，而本机这两个组件是手工装的，重复安装会因
`bin\cargo-clippy.exe` 文件占用冲突而中断整个命令。

## 已修的坑（别回退）

### 1. `dlltool` 缺失，GNU 工具链走不通

`windows` crate 全家桶在 `x86_64-pc-windows-gnu` 下需要 `dlltool` 生成 import lib，
而 rustup 的 `rust-mingw` 组件不提供它。当时的两个绕法（去掉 `clap` 默认特性、
改用纯 Rust 的 `pelite`）现在已不需要——并入了 PecoFence 的 MSVC 构建方式。

### 2. `rc.exe` 在非 ASCII 路径下静默丢图标

`rc.exe` 用 ANSI 代码页解析 `.rc` 文件，图标路径里只要有一个中文字符就读不到文件，
而且只留一条 `cargo:warning`，不报错。修法见 `crates/app/build.rs`：先把 `.ico` 复制到
`OUT_DIR`（纯 ASCII）再引用。

### 3. curl 把本地请求送进代理

机器上一旦设置 `http_proxy`，系统 `curl.exe` 会把 `127.0.0.1` 的请求也转发给代理，
结果是 502。所以本地模型模式**必须**加 `--noproxy "*"`，而云端模式**必须保留**代理
（访问境外 API 常常只能靠它）。见 `crates/llm/src/lib.rs`。

### 4. LNK 目标路径里的 `..` 导致读不到版本信息

快捷方式里可能出现 `C:\Program Files\bilibili\..\Program Files\bilibili\哔哩哔哩.exe`
这种路径，直接 `is_file()` 为假，PE 版本信息读不到。采集时要
`std::fs::canonicalize` 并剥掉 `\\?\` 前缀。

### 5. 不能用正则抓 LNK 里的路径

UTF-16 编码中的 NUL 字节会提前截断匹配，覆盖率只有 79%。必须按 ShellLinkHeader 的
LinkFlags 做完整结构解析（`crates/scan/src/lnk.rs`）。另外 PowerShell 的
`WScript.Shell` COM 实例化在某些沙箱/策略下会被拦截，不能当作通用手段。

### 6. PecoFence 的 `list` 返回形状不一致

- `fence list` → 裸数组
- `rule list` → 对象 `{defaultTarget, keepUpdated, unmatched, list: [...]}`

两处都有测试钉住，改动时别混。

## 方法论教训

1. **瓶颈是覆盖率，不是准确率。** 桌面集 97% 是手写规则调优出来的假象；换到开始菜单
   只有 70%。评估新规则时先看覆盖率。
2. **看过结果再改规则 = 数据污染。** 留出集第一轮就是这么做废的。正确顺序是：
   先跑一次干净的测量并存档，再动规则。跨数据集的数字也要标注是否参与过调优。
3. **`test` 切分只在同一数据集内有效**，跨数据集不构成独立验证。
4. **判断「这个能力有没有」之前，先确认看的是哪一层。** 同一个错误犯过两次：
   `Cond::ShortcutTarget` 在 core 里一直存在，只是 CLI 没暴露；公司名条件当时确实
   表达不了，但拿到源码后可以直接改 core。外部工具的能力边界 ≠ 代码的能力边界。
5. **`apply` 类的写操作必须能全身而退。** 先存快照、不碰 portal 栅栏、`--yes` 才动手，
   这三条是产品层面的硬约束，不是实现细节。

## 桌面图标被隐藏后怎么恢复

PecoFence 用 Explorer 的「隐藏桌面图标」把自己的图标藏起来，再在栅栏里重画。正常退出会
还原；进程被强杀时靠 watchdog 还原。如果两个都没活下来（被 `taskkill /T` 或 CI 的作业对象
一起杀掉），桌面就会变成一个图标都没有，而文件其实都在。

先看状态：

```powershell
powershell -File scripts/desktop-icons.ps1 -Status
```

`HideIcons: 1` + 没有 pecofence 进程 = 就是这种情况。恢复：

```powershell
powershell -File scripts/desktop-icons.ps1 -Show
```

它做的是向 `SHELLDLL_DefView` 发 `WM_COMMAND 0x7402`（资源管理器「查看 → 显示桌面图标」
背后同一条命令），成功后顺手删掉残留的 `icons-hidden*.marker`。

watchdog 已经不跟着应用一起死了（`spawn_detached_outside_job`）：

- `CREATE_BREAKAWAY_FROM_JOB` —— 作业对象关不掉它；
- `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` 指向 Explorer —— 按进程树杀也找不到它；
- 父进程退出后它自己还原图标并删除 marker。

实测：`--portable` 起一个实例（图标被隐藏、watchdog 的父进程是 Explorer），整个作业被强杀，
8 秒后 `HideIcons` 回到 0、marker 消失。
